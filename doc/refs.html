Refs

    Comm provides three smart pointers, called refs. A policy does two jobs - it creates and destroys the object, and it holds the reference count - and the three refs differ in who holds the policy and in whether the counting functionality is used at all.

alias class who holds the policy use it for
ref<T> coid::ref_shared each ref instance shared ownership - the default choice
iref<T> coid::ref_intrusive the object, through ref_intrusive_base::_policy_ptr shared ownership where a raw pointer must be re-adoptable
uref<T> coid::ref_unique the ref object, and only if the policy is explicitly used - it creates and destroys the object, but never counts references sole ownership, moved rather than copied

    The aliases are declared in ref_s.h, ref_i.h and ref_u.h respectively - include the one you need. The classes live in namespace coid; the aliases are global.

Choosing between them

    If the type derives from coid::ref_intrusive_base, use iref. Nothing else will work: ref_shared and ref_unique reject such types with a static_assert, because they would keep their own count alongside the object's own and neither owner would know about the other.

    Otherwise, use uref when there is exactly one owner and it can be moved - it keeps no count, and unless you name a policy no policy is allocated either. When the object needs several owners, prefer ref: it works with any type, and the object stays an ordinary object because the counting lives entirely in the ref and its policy.

    Reach for iref deliberately rather than by default. It is the right choice when the object's identity has to outlive the refs pointing at it - most of all when a raw T*, this included, must be turned back into a counted reference, which is also why intergen requires it. ref_intrusive below sets out the cases and what the base class costs.

Policies

    A policy does two separate things: it decides how the object is created and destroyed, and it carries the reference count. Every policy derives from coid::ref_policy_base, which holds the counter, and provides:

member what it does
using element_type = T; names the type get_original_ptr() points at. Required - see pointer adjustment below.
static this_type* create(...) one or more overloads returning the derived policy type. The arguments are the policy's own, so there is no fixed signature.
void on_destroy() override called when the strong count reaches zero. Disposes of the object and of the policy.
void* get_original_ptr() override the address of the object the policy counts.

    Comm ships two:

  • ref_policy_simple<T> - new on create, delete on destroy. The policy object itself is pooled.

  • ref_policy_pooled<T> - takes the object from a coid::pool<T> and returns it there instead of deleting it. Derives from ref_policy_simple.

The default policy trait

    coid::default_ref_policy_trait<T>::policy selects the policy used when you do not name one. It is ref_policy_simple<T> unless overridden:

SET_DEFAULT_REF_POLICY_TRAIT(my_type, coid::ref_policy_pooled);

    Write it at namespace scope, outside any namespace - the macro opens coid itself. Afterwards ref and iref will pool that type whenever create() does not name a policy.

    uref does not consult the trait at all. Its create() is always a plain new and the resulting ref owns no policy; to pool a uref you name the policy - create<ref_policy_pooled<T>>(). See ref_unique for why.

Creating and adopting objects

    There are two distinct things a ref can do with an object: create it through a policy, or adopt one that already exists.

ref<foo> a;
a.create();                             // through the default trait
a.create<bar>();                     // a derived type, through bar's trait
a.create<my_policy>(args);       // a named policy, args are the policy's
a.create(new foo);                // adopt
ref<foo> b(new foo);           // adopt, at construction

    The arguments to create() are the policy's, not the object's. ref_policy_simple::create() default-constructs; ref_policy_pooled::create(pool*) takes the pool to draw from. None of the policies forwards constructor arguments, and ref_policy_pooled never could - see pooling. To pass constructor arguments, build the object at the call site and adopt it: create(new foo(args)).

Adopting a raw pointer

    All three refs have an explicit constructor from a raw pointer, as std::shared_ptr and std::unique_ptr do. So:

T* p;
iref<T> r;
iref<T> a(p);                  // ok
r = p;                      // ok - assignment stays implicit
r.create(p);                // ok

iref<T> c = p;              // error - copy initialization
return p;                   // error - from a function returning iref<T>
f(p);                       // error - f takes an iref<T>
array.push(new T);       // error - container of iref<T>

    Write the ref's own type in each failing case: iref<T> c(p), return iref<T>(p), f(iref<T>(p)), array.push(iref<T>(new T)).

    What this buys, and what it does not. Assignment into a named ref stays implicit because there the target's type is visible at its declaration. At a call boundary it is not, so explicit makes the ownership transfer legible. It does not make the adoption safe: writing the explicit form and then carrying on with the raw pointer can lead to bugs, since ownership has moved into the ref and the pointer dangles once the ref dies. It catches the accident where nobody meant to transfer ownership; it says nothing about the mistake where someone did and then forgot.

    One consequence worth knowing: adopting one raw pointer into two refs or two urefs is a double free, because each adoption owns the object independently. Into two irefs it is harmless - the object already points at a policy, so the second adoption finds it and both share its count.

Comparison

    Each ref declares a single operator== against const Type*, one against nullptr_t, and a same-type operator<. There is deliberately no operator!= anywhere: C++20 synthesizes the negation and the reversed operand order from operator==, so r == p, r != p, p == r and p != r all work. Declaring operator!= in the same scope suppresses both rewritings - MSVC reports that as C7692 - so do not add one.

    operator< orders by object address. It is a total order but an arbitrary one, fine for keying a map or sorting a container, never for output that has to be reproducible.

Swapping

    Refs have no swap() of their own. Use std::swap, which works through the move constructor and the move assignment. Each step only moves pointers, so the two objects are exchanged and no reference count changes:

std::swap(a, b);                  // ok

using std::swap;
swap(a, b);                       // ok - the usual form in generic code

a.swap(b);                        // error - there is no member swap
swap(a, b);                       // error without 'using std::swap' - there is no
                                  // overload in coid for argument dependent lookup

    std::is_nothrow_swappable is false for all three refs. Their move constructors are noexcept but their move assignments are not, because an assignment releases what the ref held, and releasing the last reference to a pooled object can allocate - see pooling. A swap itself never releases anything: every assignment inside std::swap lands on a ref that has just been moved from, and is therefore empty. Generic code that checks the trait will nevertheless treat swapping two refs as an operation that may throw.

Pointer adjustment and multiple inheritance

    This is the subtlest part of the refs, and the reason policies must name element_type.

    When a class has more than one base, a base subobject does not start at the address of the whole object. Converting between the two adjusts the pointer by that offset, and the compiler does it automatically - as long as it knows both types. A void* destroys that knowledge: casting a void* to a base pointer performs no adjustment, and the result silently points into the wrong subobject. Every member read through it is off by the offset.

    get_original_ptr() returns exactly such a void*. So a policy has to declare what that pointer really is:

class my_policy : public coid::ref_policy_base
{
public:
    using element_type = T;        // required
    ...
};

    The refs cast the void* back to element_type* first and let the ordinary implicit conversion adjust it. The coid::is_ref_policy_for<Policy, Type> concept enforces the typedef's presence, so a policy without it will not satisfy create<Policy>().

    The same adjustment shows up in three other places, and all of them handle it:

  • ref<base> and ref<derived> pointing at one object hold different addresses, but compare equal, because operator== converts before comparing.

  • downcast<D>() casts from the ref's own object pointer, not from the policy's void*.

  • For an intrusive type, ref_intrusive_base itself may sit at a non-zero offset - iref<base> and iref<derived> then hold different addresses while sharing one count. ref_intrusive adjusts through the object pointer before touching the counter.

    If you write a policy whose element_type is a base of the object actually created, the policy stores the base subobject's address, and only a virtual destructor makes the eventual delete correct. Prefer naming the concrete type.

Pooling and recycling

    ref_policy_pooled<T> returns the object to a coid::pool<T> rather than deleting it. Two consequences follow from how coid::pool works:

  • A pooled object is never destructed and never reconstructed. Releasing it pushes it back as it is; taking it again hands back a live object with its previous member values. Its constructor runs exactly once, on first allocation. That is why no create() can forward constructor arguments to a pooled type - there is nothing to forward them to. Reset such an object yourself if it needs it.

  • Returning an object to a pool can allocate. pool::release_item() pushes onto a free stack whose nodes are allocated on demand, and comm's operator new throws. So releasing the last reference to a pooled object can throw, which is why the refs' move assignment operators are not noexcept while their move constructors are.

    For an intrusive type there is a third: the recycled object must let go of its policy, since the policy goes back to its own pool at the same moment and will be handed to a different object. ref_intrusive_base::clear_policy_on_recycle() does that, and ref_policy_pooled::on_destroy() calls it. Without it the next ref to adopt the recycled object would silently share some other object's count.

    So an intrusive object's _policy_ptr is null before any ref adopts it and again after it is recycled. ref_intrusive_base::has_policy() reports that, and get_strong_refcount() answers 0 rather than crashing.

Thread safety

    The reference count is atomic. A ref object is not. Same rule as std::shared_ptr, and worth stating in both directions:

safe not safe
two threads, each holding its own ref to the same object, copying and releasing freely two threads touching the same ref instance while either mutates it - for instance copying from a global ref while another thread releases it

    The unsafe case is a data race on the ref's own pointer member, and it is worse than a torn read: the copy can see the pointer as non-null, lose the race to the release that destroys the object, and then increment a counter that is already freed or back in its pool. No memory ordering fixes that, because it is a use after free rather than a visibility problem, and try_increase_strong_counter() cannot help either - the policy it would operate on may be gone. Give each thread its own ref, made while the object is guaranteed to be alive, or guard the shared one with a lock.

    Within those rules the counter's ordering is: a plain relaxed increment, since the caller already holds a reference; a release decrement paired with an acquire fence on the thread that sees the count reach zero. That pairing is what stops the destructor from running against writes made through the references just given up. It costs nothing on x86, whose stores are already ordered, and matters on weakly ordered CPUs.

ref_intrusive

    What sets iref apart is not where the count is - that is in the policy, as for ref - but that the object holds the policy pointer, in its ref_intrusive_base. The policy is created lazily, by the first ref that adopts the object, and everything else follows from those two facts.

When to use it

  • intergen interfaces require it. A host class is generated with static_assert(std::is_base_of<coid::ref_intrusive_base, T>) and the dispatcher holds its host as iref<coid::ref_intrusive_base>. If the type is an ifc_class host, the choice is already made.

  • The object has to survive a raw-pointer round trip. Any API that hands you back a T* - a C boundary, a script binding, a callback registry storing bare pointers - can be turned back into an owning reference, because the adoption finds the policy the object already points at. With ref that same round trip creates a second, independent policy, and the first release destroys the object under the other.

  • Several unrelated code paths may adopt the same object. They share one count rather than each believing it is the only owner, so adopting twice cannot double free.

  • The object has to hand out a reference to itself. A member function can return iref<T>(this) and the result joins the count the object already has. With ref this is impossible - see below.

Returning an iref from this

    A member function can give out a counted reference to its own object:

class node : public coid::ref_intrusive_base
{
public:
    iref<node> self() { return iref<node>(this); }
};

iref<node> owner(new node);
iref<node> other = owner->self();   // count is 2, one object

    The adoption finds the policy the object already points at, so the returned ref joins the existing count, and the object outlives whichever of the two is released first. This is what std::enable_shared_from_this exists for; iref needs no such helper, because the object already knows its policy.

    ref cannot do this. ref<T>(this) builds a second, independent policy - the object ends up with two counts of one each, and the first release destroys it under the other ref. Comm has no ref_shared equivalent of enable_shared_from_this, so a type that needs to return a reference to itself is a type for iref.

    Things to keep in mind:

  • The object must already be owned by an iref. Called on an object no iref has adopted yet, self() makes the returned ref its only owner, and if that ref is discarded the object is destroyed with it. So never call it from the constructor - the temporary adopts the half-built object and deletes it there and then - and never on an object that was not created with new, such as a local or a member.

  • The function cannot be const. In a const member this is const T*, and the constructor takes only T*, so iref<T>(this) does not compile there.

  • Write the ref type out. return this; does not compile, the constructor being explicit - it has to be return iref<T>(this);.

What the base class costs

    ref_intrusive_base is 16 bytes - a vptr and the policy pointer - and every instance of the type carries it whether or not it is ever reference counted. How much the type actually grows depends on whether it is polymorphic without the base:

type alone deriving from ref_intrusive_base
struct { int; } 4 24  (+20, the last 4 being padding)
struct { virtual ~; int; } 16 24  (+8)

    So the size is a small matter for a class that is already polymorphic - the vptr is shared and only the pointer is added. What is not small is the first row: a plain data type acquires a vtable, so it is not trivially copyable and cannot be memcpy'd or held in an array as raw bytes. That, rather than the byte count, is what can rule iref out for a type.

ref_unique

    A uref is a sole owner: move-only, and it never counts. It is the one ref that uses only the policy's create and destroy functionality. A policy it holds will have made the object and will destroy it again, but its counter is never touched and stays at zero for the ref's whole life; release() asserts as much.

    And the only way to get a policy here is to name one. create() therefore has two forms:

call policy what it does
uref<T>::create() none plain new T, deleted on release - whatever the trait says
uref<T>::create<derived>() none plain new derived. The stored pointer is the adjusted base one, so T needs a virtual destructor - as with create(new derived)
uref<T>::create(new T) none adopts an object you built yourself
uref<T>::create<Policy>(args) yes the only form that attaches one. args are the policy's

    Keeping the trait out of create() means a call says what it does. Whether a uref owns a policy - and so whether eject() needs its out parameter - is decided at the call site, never by a SET_DEFAULT_REF_POLICY_TRAIT line in some other header. Two calls that read identically behave identically.

    The cost is that a pooled type is not pooled through a plain uref<T>::create() - it is newed and deleted, and moving such a ref into a ref_shared gives it a ref_policy_simple that deletes it. Name the policy where that matters.

eject()

    eject() gives up ownership and returns the object pointer. If a policy is attached it must be handed over too, because an object created through a policy has to go back through it - a pooled object belongs in its pool, not on delete:

coid::ref_policy_base* policy = nullptr;
foo* object = u.eject(&policy);
...
if (policy)
    policy->on_destroy();       // finishes the handover
else
    delete object;

    Calling eject() with no out parameter on a ref that owns a policy aborts - RASSERT_FATALX, so in release builds too. That is deliberate: the alternative is to keep the policy and return the object anyway, which leaks for every caller that does not think to check, and would be indistinguishable from ejecting an empty ref.

Weak references

    Not implemented. ref_counter carries a weak counter member so the layout is already final, but its methods are commented out and nothing touches it. Implementing weak refs needs more than uncommenting them:

  • on_destroy() has to split in two - destroy the object when the strong count reaches zero, destroy the policy only when the weak count does too, so the policy outlives the object it counted. That changes ref_policy_pooled in particular, which currently returns object and policy to their pools in one go.

  • The weak counter's memory ordering is a placeholder. What it has to pair with depends on how lock() and the split destruction are written.

  • ref_intrusive_base holds a bare policy pointer and has nowhere to record that its object is gone while its policy is not.

    try_increase_strong_counter() exists for the eventual lock(). Its only caller today is the ref_shared downcast helper, where the count provably cannot be zero.

Writing your own policy

template<class T>
class ref_policy_nodelete : public coid::ref_policy_base
{
    using this_type = ref_policy_nodelete<T>;
public:
    using element_type = T;

    static this_type* create(T* object_ptr) {
        this_type* p = new this_type;
        p->_object_ptr = object_ptr;
        return p;
    }

    void on_destroy() override { delete this; }    // object outlives us
    void* get_original_ptr() override { return _object_ptr; }

protected:
    T* _object_ptr = nullptr;
};

    Points to keep in mind:

  • element_type is not optional, and create() must be your own - ref_policy_base declares none, so a missing one is a compile error rather than a null policy.

  • on_destroy() is responsible for the policy as well as the object. Whatever it does, the policy must not be left alive with nothing referring to it.

  • The counter is at zero when on_destroy() runs, and must stay there.
